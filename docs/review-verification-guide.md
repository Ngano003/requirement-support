# レビュー機能検証手順書

## 目的

要件定義レビュー機能のプロンプト設計を、主要なLLMモデルで検証し、抜け漏れ・矛盾検出の精度を評価する。

## 検証対象モデル

1. **GPT-4o** (OpenAI)
2. **Gemini 2.0 Flash Thinking** (Google)
3. **Claude Sonnet 4** (Anthropic)
4. **Qwen2.5-Coder-32B** (Alibaba)

## 検証用サンプル要件定義書

以下のサンプルは、意図的に抜け漏れと矛盾を含んでいます。

### サンプル1: 社内書籍管理システム（抜け漏れ多）

```markdown
# 社内書籍管理システム 要件定義書

## 1. システム概要
社内の技術書・ビジネス書を管理し、社員が予約・貸出できるWebアプリケーション。

## 2. 目的・背景
現在、書籍管理をExcelで行っているが、以下の課題がある：
- 誰が借りているか不明
- 予約ができない
- 在庫状況がわからない

## 3. 対象ユーザー
全社員（約100名）

## 4. 機能要件

### 4.1 書籍検索機能
- タイトル、著者名で検索できる
- 検索結果を一覧表示する

### 4.2 書籍貸出機能
- 書籍を借りる際に貸出記録を登録する
- 返却予定日を設定する

### 4.3 予約機能
- 貸出中の書籍を予約できる
- 予約者には返却時に通知する

## 5. 制約条件
- 予算: 200万円以内
- 納期: 3ヶ月後
- 既存のExcelデータを移行する
```

**想定される問題**:
- 抜け漏れ: 非機能要件が無い、ログイン機能が無い、管理者機能が無い、エラーハンドリング未定義
- 矛盾: 対象ユーザーは「全社員」だが管理者の定義が無い

### サンプル2: ECサイト（矛盾多）

```markdown
# ECサイト 要件定義書

## 1. システム概要
一般消費者向けのオンラインショッピングサイト。全商品を無料で公開。

## 2. 目的・背景
売上向上のため、オンライン販売チャネルを開設する。

## 3. 対象ユーザー
- 一般消費者
- 会員ユーザー

## 4. 機能要件

### 4.1 会員登録機能
- メールアドレス、パスワード、氏名、住所を入力
- パスワードは6文字で固定
- 登録後、自動的にログイン状態にする

### 4.2 商品閲覧機能
- 全商品を誰でも閲覧できる
- 商品の詳細情報（価格、在庫、説明）を表示
- 会員のみ閲覧可能

### 4.3 カート機能
- 商品をカートに追加する
- カート内の商品数量を変更する
- ユーザーIDは手動で入力する

### 4.4 決済機能
- クレジットカード決済に対応
- リアルタイムで在庫を更新する

## 5. 非機能要件

### 5.1 セキュリティ
- パスワードは8文字以上で英数字を含む
- 全データを暗号化する

### 5.2 パフォーマンス
- 検索結果は高速に表示する
- バッチ処理で1日1回在庫を更新する

## 6. 制約条件
- 開発期間: 1ヶ月
- 予算: 50万円
```

**想定される問題**:
- 矛盾1: システム概要「全商品を無料で公開」vs 目的「売上向上」
- 矛盾2: 「全商品を誰でも閲覧」vs「会員のみ閲覧可能」
- 矛盾3: パスワード「6文字で固定」vs「8文字以上」
- 矛盾4: 「リアルタイム更新」vs「1日1回バッチ更新」
- 矛盾5: 「ユーザーIDは手動入力」vs「自動ログイン」
- 抜け漏れ: ログアウト機能、注文履歴、配送管理等

### サンプル3: 勤怠管理システム（バランス型）

```markdown
# 勤怠管理システム 要件定義書

## 1. システム概要
社員の出退勤時刻を記録し、勤怠データを集計するWebアプリケーション。

## 2. 目的・背景
紙のタイムカードから脱却し、勤怠管理を効率化する。

## 3. 対象ユーザー
- 一般社員: 出退勤の打刻
- 管理者: 勤怠データの確認・承認

## 4. 機能要件

### 4.1 出勤打刻機能
- 社員が出勤時刻を記録する
- 位置情報を記録する（オフィス内からのみ打刻可能）

### 4.2 退勤打刻機能
- 社員が退勤時刻を記録する

### 4.3 勤怠一覧表示機能
- 管理者が全社員の勤怠データを一覧表示する
- 月別、社員別で絞り込み可能

### 4.4 承認機能
- 管理者が勤怠データを承認する

## 5. 非機能要件

### 5.1 セキュリティ
- 認証にはメールアドレスとパスワードを使用
- セッションタイムアウトは8時間

### 5.2 パフォーマンス
- 打刻処理は1秒以内に完了する

## 6. 制約条件
- 既存の給与システムとCSV連携する
- スマートフォンからもアクセス可能にする
```

**想定される問題**:
- 抜け漏れ: 打刻修正機能、休暇申請、エラーハンドリング、データバックアップ
- 矛盾: 軽微（位置情報チェックの詳細が不明確）

```
[全体的な抜け漏れの深刻度と優先対応項目]
```

### ステップ2: 矛盾検出の検証

#### プロンプト（矛盾検出用）

```
あなたは要件定義のレビュー専門家です。
以下の要件定義書を分析し、矛盾・不整合を指摘してください。

【要件定義書】
[ここにサンプル1, 2, 3のいずれかを貼り付け]

【チェック観点】

1. セクション間の矛盾
   - システム概要で言及されている内容と、機能要件の内容が一致しているか
   - 対象ユーザーで定義されたユーザー種別が、機能要件で実際に使われているか
   - 制約条件と機能要件が両立可能か

2. 用語の不統一
   - 同じ概念が異なる用語で表現されている
     例: 「ユーザー」「利用者」「会員」の混在
   - 表記ゆれ
     例: 「ログイン」「ログ イン」「log in」

3. 論理的矛盾
   - 同時に満たせない要件
     例: 「全データを公開」と「認証ユーザーのみアクセス可」
   - 制約の矛盾
     例: 「パスワードは8文字以上」と「パスワードは6文字で固定」
   - データの矛盾
     例: 「ユーザーIDは自動採番」と「ユーザーIDは手動入力」
   - 処理フローの矛盾
     例: 「リアルタイムで更新」と「1日1回バッチ更新」

【出力形式】
以下の形式で、発見した矛盾を報告してください：

## 矛盾・不整合一覧

### 1. セクション間の矛盾
- [矛盾箇所]: [重要度(高/中/低)]

  - セクション2: [記述内容2]

  - 解決策: [どちらかを修正する提案]

### 2. 用語の不統一
- [概念名]: [重要度]
  - 使用されている用語: [用語1, 用語2, ...]
  - 出現箇所: [セクション名]
  - 推奨: [統一すべき用語]

### 3. 論理的矛盾
- [矛盾内容]: [重要度]
  - 要件A: [内容]
  - 要件B: [内容]
  - 矛盾理由: [なぜ矛盾するか]
```

2. **矛盾検出**
   - 各LLMに「矛盾検出用プロンプト + サンプル1」を入力

## 検証後のアクション

### 優秀なモデルの選定

検証結果を基に、以下を決定：

1. **本番採用モデル**: 総合評価が最も高いモデル
2. **フォールバックモデル**: 2番目に高いモデル
3. **プロンプト改善**: 誤検出が多かった項目についてプロンプトを改善

### プロンプト改善

検出率が低かった項目について、プロンプトに以下を追加：

- Few-Shot Examples（良い検出例・悪い検出例）
- より具体的なチェックポイント
- 重要度判定の基準

### 実装への反映

- 選定したモデルを`backend/app/services/review_service.py`に統合
- プロンプトテンプレートを`backend/app/prompts/`に配置
- 検証で得られた知見をドキュメントに反映

## 検証実施時の注意事項

1. **公平性の確保**
   - 全モデルに同じプロンプトを使用
   - 同じ順序でサンプルを検証
   - 応答時間は3回測定して平均値を取る

2. **バイアスの排除**
   - 事前に正解を見ずに評価
   - 複数人で評価し、合議で決定

3. **記録の詳細化**
   - スクリーンショットを保存
   - 回答全文をテキストで保存
   - 判断が難しい検出は備考欄に記載

4. **追加検証**
   - 検出率が低い場合、プロンプトを調整して再検証
   - 誤検出が多い場合、原因を分析
