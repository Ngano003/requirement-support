## 1. はじめに

### 1.1 目的

本文書は、オフィスビル向けスマートビルディング管理システムの要件を定義するものである。本システムは、IoTセンサーネットワークを活用し、空調・照明・セキュリティ・エネルギー管理を統合的に制御し、快適性の向上と省エネルギー化を実現する。

### 1.2 適用範囲

本要件定義書は、以下のシステムに適用される:
- IoTゲートウェイ装置
- 各種センサーノード（温湿度、照度、人感、CO2等）
- アクチュエーター制御ノード（空調、照明、ブラインド等）
- クラウド管理プラットフォーム
- 管理用Webアプリケーション
- モバイルアプリケーション

### 1.3 対象ビル仕様

| 項目 | 仕様 |
|------|------|
| 対象規模 | 地上10階建て、延床面積 15,000㎡ |
| フロア構成 | 1F: エントランス・店舗、2-9F: オフィス、10F: 機械室 |
| 想定入居テナント数 | 15社 |
| 想定在館者数 | 最大800名 |
| IoTデバイス総数 | 約1,500台 |

### 2.2 システム機能概要

1. **環境監視機能**: 温湿度、照度、CO2濃度、騒音レベル等の常時監視
2. **空調制御機能**: 在室状況とスケジュールに基づく最適空調制御
3. **照明制御機能**: 人感センサーと照度センサーによる自動調光・消灯
4. **セキュリティ機能**: 入退室管理、不審者検知、異常通知
5. **エネルギー管理機能**: 電力使用量の可視化と省エネ制御
6. **故障検知機能**: 機器異常の早期検出と通知
7. **レポート機能**: 日次・月次のエネルギー使用状況レポート

### 2.3 システム性能目標

| 項目 | 目標値 |
|------|--------|
| センサーデータ収集周期 | 1分 |
| 制御コマンド応答時間 | 3秒以内 |
| クラウド連携遅延 | 10秒以内 |
| システム稼働率 | 99.5%以上 |
| 省エネ効果 | 従来比30%削減 |
| 同時接続デバイス数 | 2,000台 |

## 3. 機能要件

### 3.1 IoTゲートウェイ機能

#### 3.1.1 基本機能

**REQ-GW-001**: ゲートウェイは、配下のIoTデバイスとの通信を管理すること
- 対応プロトコル: BLE 5.0, LoRaWAN, Zigbee
- 最大接続デバイス数: 500台/ゲートウェイ
- 通信範囲: BLE 30m、LoRaWAN 1km

**REQ-GW-002**: ゲートウェイは、収集したセンサーデータをクラウドに送信すること
- 送信プロトコル: MQTT over TLS 1.2
- 送信周期: 1分間隔（バッチ送信）
- データ形式: JSON

**REQ-GW-003**: ゲートウェイは、クラウドからの制御コマンドを受信し、対象デバイスに転送すること
- 受信プロトコル: MQTT
- コマンド応答時間: 3秒以内
- 対象デバイス: 照明、空調、ブラインド制御ノード

**REQ-GW-004**: ゲートウェイは、ローカルでのエッジ処理機能を持つこと
- 処理内容: 異常値検出、閾値判定、簡易制御ロジック
- 処理周期: リアルタイム（データ受信時）
- ローカル制御遅延: 1秒以内

**REQ-GW-005**: ゲートウェイは、ネットワーク断時にローカル動作を継続すること
- ローカルデータ保存: 最大24時間分
- 復旧時動作: 蓄積データを自動送信
- ローカル制御: 事前設定ルールに基づき継続

#### 3.1.2 セキュリティ機能

**REQ-GW-010**: ゲートウェイは、デバイス認証機能を持つこと
- 認証方式: 証明書ベース認証
- 未認証デバイス: 接続拒否
- 認証更新周期: 30日

**REQ-GW-011**: ゲートウェイは、クラウドとの通信を暗号化すること
- 暗号化方式: TLS 1.2以上
- 証明書: サーバー証明書による認証
- 暗号スイート: AES-256-GCM推奨

**REQ-GW-012**: ゲートウェイは、不正アクセスを検知・記録すること
- 検知対象: 認証失敗、異常なコマンド、通信異常
- 記録内容: タイムスタンプ、送信元、内容
- 通知: 重大な不正アクセスはクラウドに即時通知

#### 3.1.3 保守機能

**REQ-GW-020**: ゲートウェイは、OTAファームウェア更新に対応すること
- 更新トリガー: クラウドからの指示
- 更新タイミング: 深夜時間帯（2:00-4:00）
- ロールバック: 更新失敗時に自動復帰

**REQ-GW-021**: ゲートウェイは、自己診断機能を持つこと
- 診断項目: CPU、メモリ、ストレージ、ネットワーク、無線モジュール
- 診断周期: 1時間毎
- 異常検出時: クラウドへ通知、ローカルログ記録

**REQ-GW-022**: ゲートウェイは、稼働状態をクラウドに定期報告すること
- 報告周期: 5分毎
- 報告内容: 稼働時間、接続デバイス数、CPU/メモリ使用率、通信状態
- タイムアウト: 15分間応答なしで異常と判定

### 3.2 センサーノード機能

#### 3.2.1 温湿度センサーノード

**REQ-SN-001**: 温湿度センサーノードは、室温と湿度を測定すること
- 温度測定範囲: -10℃ ~ +50℃
- 温度測定精度: ±0.3℃
- 湿度測定範囲: 10% ~ 90% RH
- 湿度測定精度: ±3% RH

**REQ-SN-002**: 温湿度センサーノードは、測定データをゲートウェイに送信すること
- 送信周期: 1分
- 送信プロトコル: BLEAdvertisingまたはLoRaWAN
- データ形式: バイナリ（温度2byte、湿度2byte）

**REQ-SN-003**: 温湿度センサーノードは、低消費電力動作を行うこと
- 動作モード: スリープ→測定→送信→スリープのサイクル
- 平均消費電流: 50μA以下
- 電池寿命: 3年以上（CR2032電池使用時）

#### 3.2.2 CO2センサーノード

**REQ-SN-010**: CO2センサーノードは、室内CO2濃度を測定すること
- 測定範囲: 400 ~ 5000 ppm
- 測定精度: ±50ppm または±5%のいずれか大きい方
- 応答時間: T90 < 120秒

**REQ-SN-011**: CO2センサーノードは、測定データをゲートウェイに送信すること
- 送信周期: 5分
- 送信プロトコル: LoRaWAN
- 高濃度検出: 1000ppm超過時は1分周期に変更

**REQ-SN-012**: CO2センサーノードは、自動キャリブレーション機能を持つこと
- キャリブレーション方式: ABC（Automatic Baseline Correction）
- キャリブレーション周期: 7日毎
- 基準値: 400ppm（外気相当）

#### 3.2.3 人感センサーノード

**REQ-SN-020**: 人感センサーノードは、人の存在を検知すること
- 検知方式: PIR（焦電型赤外線）センサー
- 検知範囲: 5m、110°
- 検知感度: 人の移動を検知

**REQ-SN-021**: 人感センサーノードは、検知イベントをゲートウェイに送信すること
- 送信タイミング: 人検知時、無人検知時（5分間無検知後）
- 送信プロトコル: BLE
- データ内容: ノードID、検知状態、タイムスタンプ

**REQ-SN-022**: 人感センサーノードは、照度センサーを統合すること
- 測定範囲: 0 ~ 10,000 lux
- 測定精度: ±10%
- 送信周期: 人感検知時に照度も同時送信

#### 3.2.4 電力センサーノード

**REQ-SN-030**: 電力センサーノードは、分電盤の電力使用量を測定すること
- 測定方式: CTセンサー（クランプ式電流センサー）
- 測定範囲: 0 ~ 200A（AC100V/200V）
- 測定精度: ±2%

**REQ-SN-031**: 電力センサーノードは、測定データをゲートウェイに送信すること
- 送信周期: 10秒
- 送信データ: 電流値、電圧値、電力値、力率
- 送信プロトコル: 有線LAN（Ethernet）またはRS-485

**REQ-SN-032**: 電力センサーノードは、異常検出機能を持つこと
- 検出対象: 過電流、電圧異常、力率低下
- 閾値: 定格電流の110%、電圧±10%、力率0.8以下
- 検出時動作: 即時ゲートウェイに通知

### 3.3 アクチュエーター制御機能

#### 3.3.1 空調制御

**REQ-AC-001**: システムは、各エリアの空調を個別制御すること
- 制御単位: 50㎡あたり1ゾーン
- 制御パラメータ: 設定温度、風量、運転モード
- 制御方式: 既存空調システムのリモコン信号をエミュレート

**REQ-AC-002**: システムは、在室状況に基づき空調を自動制御すること
- 在室判定: 人感センサーによる検知
- 在室時動作: 設定温度で運転
- 不在時動作: 30分不在で省エネモード、2時間不在で停止

**REQ-AC-003**: システムは、スケジュールに基づき空調を制御すること
- スケジュール設定: 平日/休日、時間帯別
- 事前運転: 始業30分前から運転開始
- 終業後: 終業30分後に停止

**REQ-AC-004**: システムは、CO2濃度に基づき換気制御を行うこと
- 換気開始閾値: CO2濃度1000ppm超過
- 換気停止閾値: CO2濃度800ppm以下
- 換気方法: 外気取入量増加または窓開閉制御

**REQ-AC-005**: システムは、空調制御の省エネ最適化を行うこと
- 最適化手法: AI学習による予測制御
- 学習データ: 過去の在室パターン、外気温、電力使用量
- 目標: エネルギー消費量を従来比30%削減

#### 3.3.2 照明制御

**REQ-LT-001**: システムは、各エリアの照明を個別制御すること
- 制御単位: 30㎡あたり1ゾーン
- 制御方式: DALI（Digital Addressable Lighting Interface）
- 制御内容: ON/OFF、調光（0-100%）

**REQ-LT-002**: システムは、人感センサーに基づき照明を自動制御すること
- 人検知時: 照明点灯
- 無人検知時: 5分後に消灯
- 調光制御: 照度センサーにより自然光を考慮

**REQ-LT-003**: システムは、照度センサーに基づき自動調光すること
- 目標照度: デスク面500lux
- 調光範囲: 30% ~ 100%
- 応答時間: 照度変化から30秒以内に調整完了

**REQ-LT-004**: システムは、スケジュールに基づき照明を制御すること
- スケジュール設定: 平日/休日、時間帯別
- 始業時: 自動点灯
- 終業時: 1時間後に一斉消灯（残業者検知時は継続点灯）

#### 3.3.3 ブラインド制御

**REQ-BL-001**: システムは、電動ブラインドを自動制御すること
- 制御対象: 南側・西側の窓
- 制御方式: モーター駆動（開/閉/中間位置）
- 制御パラメータ: 開度0-100%

**REQ-BL-002**: システムは、日射量に基づきブラインドを自動制御すること
- 制御条件: 照度センサー値が10,000lux以上
- 動作: ブラインドを50%閉
- 目的: 日射遮蔽による空調負荷低減、眩しさ軽減

**REQ-BL-003**: システムは、手動操作を優先すること
- 手動操作検出: ブラインド位置センサー
- 優先期間: 手動操作から2時間は自動制御を停止
- 復帰: 2時間経過後に自動制御再開

### 3.4 エネルギー管理機能

#### 3.4.1 計測・記録機能

**REQ-EM-001**: システムは、電力使用量を計測・記録すること
- 計測ポイント: ビル全体、フロア別、テナント別、用途別（空調/照明/コンセント）
- 計測周期: 10秒
- 記録周期: 1分平均値をクラウドに記録

**REQ-EM-002**: システムは、ガス・水道使用量を計測・記録すること
- 計測方式: パルスカウンター
- 計測周期: パルス発生時
- 記録周期: 1時間累積値

**REQ-EM-003**: システムは、外気温・日射量を計測・記録すること
- センサー設置: 屋上
- 計測項目: 外気温、外気湿度、日射量、風向・風速
- 記録周期: 10分

**REQ-EM-004**: システムは、計測データを長期保存すること
- 保存期間: 5年間
- データ粒度: 10分平均値、1時間平均値、日次合計値、月次合計値
- ストレージ: クラウドストレージ

#### 3.4.2 可視化機能

**REQ-EM-010**: システムは、電力使用状況をリアルタイムで表示すること
- 表示内容: 現在の電力使用量、前日同時刻比、前年同月比
- 表示形式: グラフ（時系列、内訳円グラフ）
- 更新周期: 1分

**REQ-EM-011**: システムは、エネルギー使用量のレポートを生成すること
- レポート種類: 日報、週報、月報、年報
- 出力形式: PDF、Excel
- 配信方法: メール自動送信、ダウンロード

**REQ-EM-012**: システムは、テナント別のエネルギー使用量を表示すること
- 表示単位: テナント別、フロア別
- 比較機能: 前月比、前年同月比、ビル平均との比較
- アクセス権限: テナントは自社分のみ閲覧可能

#### 3.4.3 分析・最適化機能

**REQ-EM-020**: システムは、エネルギー使用パターンを分析すること
- 分析内容: ピーク時間帯、ベースロード、季節変動
- 分析手法: 機械学習による傾向分析
- 出力: 分析レポート、改善提案

**REQ-EM-021**: システムは、省エネ目標の達成状況を管理すること
- 目標設定: 月次・年次の削減目標（前年比%）
- 進捗管理: 目標との差異を可視化
- アラート: 目標未達の恐れがある場合に通知

**REQ-EM-022**: システムは、デマンドレスポンス機能を持つこと
- 対応内容: 電力会社からの削減要請に対応
- 削減手段: 空調設定温度調整、照明照度低減
- 削減量: 最大20%削減可能

### 3.5 セキュリティ機能

#### 3.5.1 入退室管理

**REQ-SEC-001**: システムは、ICカードによる入退室管理を行うこと
- 対応カード: FeliCa（Suica、PASMO等）、MIFARE
- 認証方式: カードIDによる認証
- 認証時間: カードタッチから0.5秒以内

**REQ-SEC-002**: システムは、入退室履歴を記録すること
- 記録内容: カードID、氏名、入退室時刻、ドアID
- 記録保存: 3年間
- 検索機能: 日時・人物・ドアでの絞り込み検索

**REQ-SEC-003**: システムは、権限管理機能を持つこと
- 権限設定: 人物別・ドア別・時間帯別にアクセス権限設定
- 権限パターン: 一般社員、管理者、清掃業者、来客等
- 権限更新: リアルタイムで反映（5分以内）

**REQ-SEC-004**: システムは、不正入退室を検知・通知すること
- 検知対象: 未登録カード、権限外ドアへのアクセス、異常時間帯のアクセス
- 通知先: 管理者スマートフォン、警備室
- 通知方法: プッシュ通知、メール

#### 3.5.2 監視カメラ連携

**REQ-SEC-010**: システムは、監視カメラと連携すること
- カメラ台数: 各フロア4台、計40台
- 解像度: フルHD（1920x1080）以上
- 録画保存: 30日間

**REQ-SEC-011**: システムは、異常検知時に録画を開始すること
- 検知トリガー: 入退室異常、深夜時間帯の人感検知
- 録画内容: トリガー前30秒から後5分間
- 保存場所: ローカルストレージ

**REQ-SEC-012**: システムは、顔認証機能を持つこと
- 認証方式: AI顔認証エンジン
- 認証精度: FAR < 0.1%, FRR < 1%
- 処理時間: 1秒以内

#### 3.5.3 異常検知

**REQ-SEC-020**: システムは、火災を検知すること

- 取得データ: 30分毎の電力使用量、デマンド予測
- 送信データ: デマンドレスポンス対応実績

**REQ-IF-EXT-003**: システムは、気象情報サービスと連携すること
- 連携方式: Web API
- 取得データ: 天気予報、気温予報、降水確率
- 更新周期: 3時間毎

**REQ-IF-EXT-004**: システムは、カレンダーサービスと連携すること
- 連携サービス: Google Calendar、Microsoft 365
- 取得データ: 会議室予約、テナント休業日
- 活用: 空調事前運転、照明自動点灯

## 8. 試験要件

### 8.1 単体試験

**REQ-TEST-001**: 全てのソフトウェアモジュールは単体試験を実施すること
- カバレッジ目標: C0カバレッジ 80%以上
- テストフレームワーク: Jest（JavaScript）、pytest（Python）
- 自動化: CI/CDパイプラインで自動実行

**REQ-TEST-002**: IoTデバイスのファームウェアは単体試験を実施すること
- テスト環境: 実機またはエミュレーター
- テスト項目: センサー読取、通信、省電力モード
- 記録: テスト結果を記録、トレーサビリティ確保

### 8.2 結合試験

**REQ-TEST-010**: システム間の結合試験を実施すること
- テスト対象: ゲートウェイ-クラウド間、センサー-ゲートウェイ間
- テスト項目: 通信正常性、異常時動作、性能
- テスト環境: テスト用クラウド環境

**REQ-TEST-011**: 負荷試験を実施すること
- テスト内容: 想定デバイス数の1.5倍（2,250台）での動作確認
- 測定項目: 応答時間、エラー率、リソース使用率
- 合格基準: 性能要件を満たすこと

### 8.3 システム試験

**REQ-TEST-020**: 実環境での検証を実施すること
- 検証期間: 本番稼働前に3ヶ月間
- 検証内容: 全機能の動作確認、長期安定性
- 検証場所: パイロットフロア（1フロア）

**REQ-TEST-021**: セキュリティ試験を実施すること
- 試験内容: 脆弱性診断、ペネトレーションテスト
- 実施時期: リリース前
- 合格基準: 重大な脆弱性ゼロ

**REQ-TEST-022**: ユーザビリティテストを実施すること
- 被験者: 管理者5名、テナントユーザー10名
- テスト内容: UI操作性、分かりやすさ
- 評価基準: SUS（System Usability Scale）スコア70以上

### 8.4 受入試験

**REQ-TEST-030**: 顧客による受入試験を実施すること
- 試験項目: 全ての機能要件、非機能要件
- 試験期間: 2週間
- 合格基準: 全項目が要件を満たすこと

- 出力: 電波法に準拠した出力レベル

- フェーズ1: 2フロアでパイロット運用（3ヶ月）
